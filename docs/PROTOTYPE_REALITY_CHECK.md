# Prototype reality check and removal of scripted results

Reviewed 16 November 2026. This assessment describes the current source code, isolated tests and explicitly identified historical evidence. No new live LLM evaluation was run.

## What was removed

1. `src/personal_api.py` no longer routes matched questions through prepared fixtures. All personal questions now call `pipeline.ask(question, mode)` in the active workspace. The removed matcher covered eight canonical questions and broader keyword matches. Its responses varied by selected mode without executing those retrieval modes. It supplied manufactured chunk IDs, fixed timing values and pre-set approval, confidence and citation-verification flags.
2. Deleted `src/demo_fixtures.py` and `src/doc_comparison.py`, plus their generated bytecode. These were active scripted-result modules, not the isolated synthetic tests.
3. Removed `/personal/compare/prepared` and its authentication exception in `src/server.py`. The endpoint returned the same prepared comparison regardless of selected workspace or uploaded versions.
4. Removed the prepared comparison cards, fixed version descriptions, filters, fabricated progress messages and minimum 3.4-second delay from `web/personal.js` and `web/index.html`. The Document Changes view now uses the existing `/versions` → `/rules/extract` → `/changes` workflow.
5. Corrected citation rendering: a cited chunk is now found by ID, not assumed to occupy the same array position as the citation. A first citation to C2 therefore displays C2's evidence. Restored the established personal-source trust notice and its test expectation.

Suggested questions, legitimate exact-answer/HyDE caches, scoped retrieval, and clearly labelled synthetic test/demo utilities remain. Static historical documentation was not rewritten to pretend the shortcuts never existed. No live answer cache was cleared: the removed fixture route returned directly and did not itself populate the normal answer cache.

## Current dataset prerequisites

Read-only personal-registry inspection found one real personal document:

- `BTech_(Rules_&_Regulations)2013_21nov2023.pdf`: indexed, registry count **114 chunks**.
- No retained historical version for that document.

## Why the real features can fail or look as though they fail

| Finding | Evidence and confidence | Consequence | Recommended correction |
|---|---|---|---|
| Correct retrieval can still lead to abstention | Previously reported page-10 incident; current `answer.generate_answer`, `validate_answer` | RAG is a pipeline, not just vector retrieval. Provider errors, context selection and validation are distinct failure stages. | Preserve stage-specific failure reasons in the UI and diagnostics; classify each failing case before changing prompts or thresholds. |
| Validation is too brittle for natural answers | Reproduced offline: the accepted complete answer fails after replacing “on or before” with equivalent “no later than”. `evidence.claim_failures` reports unsupported claims and omitted qualifications. | Good paraphrases are rejected, making an accurate retriever appear broken. The stricter validator added earlier contributed to this trade-off. | Prefer a source-extractive answer baseline. Validate structured condition/value/unit/applicability/authority/deadline records and their evidence spans, with paraphrase regression cases. Do not simply remove checks or lower thresholds. |
| Whole-provision selection can refuse otherwise useful evidence | `answer.trim_chunk_span` selects one provision per active block and refuses selected text over `CHUNK_MAX_TOKENS * 4`; generation currently refuses if any active excerpt is empty. | One oversized block can block the whole answer. Multi-provision or cross-page questions may lose necessary coverage. | Track completeness/continuations and select a sufficient evidence set under a total budget. Fail only when required evidence is missing, not because an irrelevant candidate is oversized. Test condition retention. |
| Rule extraction cannot express some source comparisons reliably | Offline B11.4 probe: candidate filter accepts the provision, but `RELATIONS['>=']` does not recognize its “80% or more” / “does not fall below 75%” wording. | A correctly proposed threshold rule can be discarded. Rule Book and comparison can then be empty or incomplete. | Add operator/negation patterns with tests for these exact phrases and bind each operator to its own value and applicability—not any operator and number somewhere in the same quote. |
| Failed rule extraction can be marked complete | `intelligence.extract_rules` unconditionally saves `partial=False` after the batch loop, including the `failed` branch. Exhausted provider-unavailable retries can also fall through without an explicit terminal batch failure. | A partial or empty result can become a cached “complete” result; later runs may skip necessary extraction. | Preserve partial/error status on every failed batch, checkpoint accepted rules, resume missing batches, and show incomplete comparison explicitly. This issue is documented, not silently repaired as part of shortcut removal. |
| Actual comparison is narrower than the old screen advertised | `intelligence.diff_rules` compares extracted numeric rule tables by subject/unit/applicability and selected fields. | It is not a full PDF diff; nonnumeric structural changes may never appear. Model variation in subject/applicability wording can look like additions/removals. | Label the scope honestly (now restored). Stabilize rule identities and extraction first. If whole-document comparison is required, separately align clauses and cite both versions; do not market a rule-table diff as that feature. |
| Provider limits affected previous experiments | Historical `improve_hyde/HYDE_REPORT.md` records 413, 429, daily token exhaustion and empty-content failures. | Slow/failed HyDE and extraction calls need not be retrieval defects. | Budget calls, cap/resume retries, surface provider failures separately and evaluate availability before live demos. Current quota/availability was not rechecked; these historical failures do not prove today's provider is unavailable. |
| Comparison can duplicate HyDE work | `server.compare_endpoint` concurrently calls raw, HyDE and Fusion; Fusion calls raw and HyDE again. HyDE cache read/write locking is not an in-flight request coalescer. | Cold comparisons may generate the same HyDE twice and repeat local embedding/search work, increasing cost and latency. | Generate one request-scoped raw result and one HyDE result, then compute Fusion from them. Keep independent evaluation runs explicit where required. |
| Answer caching can conceal mode differences | Production answer lookup uses normalized question/workspace/source identity, not retrieval mode; a hit bypasses retrieval and returns the saved evidence. | Switching Raw/HyDE/Fusion can show the same valid cached answer. That is not proof that all three methods retrieved identically. | Bypass answer caching for explicit comparisons/benchmarks; expose original mode/provenance or include mode in cache policy where the UI promises a fresh method comparison. |
| HyDE superiority has not been established | The saved ablation is incomplete and records only one paired experimental V1/V2 case, not a completed held-out acceptance result. | It is unjustified to claim Fusion/HyDE improves this dataset or that mode-specific scripted responses measure it. | Evaluate Raw first, then HyDE and Fusion on the same human-reviewed held-out set. Measure retrieval separately from answer correctness, abstention, latency and provider failures. |

## Honest strength assessment

**This is a substantial engineering prototype, but not yet a dependable policy-answering product.** The backend is not merely a façade: scoped storage/retrieval, source inspection, version cataloguing, citations, deterministic what-if arithmetic and many safety paths have automated coverage. Removing the shortcuts exposes these real mechanisms instead of making them disappear.

The strongest parts are the breadth of implementation, visible source evidence, scoped data access and willingness to abstain. The weakest part is demonstrated end-to-end reliability on real questions: evidence selection, numerical rule interpretation, answer validation, provider limits and extraction completeness interact poorly. The feature surface is ahead of the quality evidence.

Passing hundreds of mocked/isolated tests does not establish real-model accuracy, useful-answer rate or safe eligibility judgments. The scripted responses were especially misleading because their confidence/verification flags resembled live checks, and their institution-specific content could be returned to an unrelated valid personal workspace. Those paths are now removed. Remaining authentication is a local capability-workspace prototype, not a complete production user/role system.

I would present this as a **source-grounded campus-policy research prototype with known reliability limits**, not an autonomous eligibility authority or a validated benchmark winner. A numeric “strength score” would suggest precision this review does not support.

## Fix order

1. **Honesty and routing — completed here.** Remove canned answers/report/progress and authentication bypass. Restore real calls, source identity and truthful empty/error states.
2. **Reliable extraction and comparison prerequisites.** Fix partial-result persistence and operator parsing with isolated failure/retry tests. Supply two real versions before evaluating comparison. Do not change existing data without a separately authorized update.
3. **Reliable answering.** Start with exact cited source provisions for a small set of real questions. Improve completeness selection and structured condition validation; add accepted-paraphrase and rejected-contradiction cases. Retain safe abstention.
4. **Measured retrieval.** Build a small human-reviewed held-out set covering direct facts, paraphrases, multi-condition questions, conflicts and out-of-scope requests. Report retrieval Recall@k/MRR separately from correct-answer coverage, unsupported-answer rate and abstention quality. No invented labels or results.
5. **Cost and responsiveness.** Coalesce duplicate HyDE generation, bound request-wide retries, show truthful progress and preserve resumable extraction state. Test fresh and cached paths separately.
6. **Production readiness, if needed.** Add authenticated users/roles, deployment/storage concurrency controls, auditability, backups, upload security and load tests. These are future requirements, not reasons to add more dashboard features now.

## Verification and limitations of this review

Before removal: `python -m pytest tests/ -q` produced **352 passed, 1 failed** (personal frontend trust-notice expectation).

After removal:

```sh
python -m pytest tests/ -q
node --check web/personal.js
node tests/personal_frontend.test.cjs
node tests/sidebar_frontend.test.cjs
node tests/frontend.test.cjs
node tests/whatif_frontend.test.cjs
```

Results: **382 Python tests passed**, six dependency deprecation warnings; all four JavaScript suites passed, including 19 dashboard checks. Added 29 endpoint regressions covering all eight former canned questions across three modes, empty workspaces, removal of the prepared endpoint/auth exception and real comparison delegation. Added frontend regression coverage for non-first cited-source mapping and removal of the prepared comparison control.

SHA-256 snapshots of all **244** files under `data/`, `.chroma/` and `.chroma-institutions/` were identical before and after. No live provider requests, indexing, embeddings, cache clears or database writes were performed. Live provider availability and visual browser behavior were not newly tested; JavaScript validation used the existing DOM harnesses. No claim is made that the real model now answers all former scripted questions correctly.

Source changes take effect after the running Python server reloads/restarts and the browser reloads its JavaScript. If using `python -m src.server`, stop and restart that process from the project directory, then hard-refresh the page.
